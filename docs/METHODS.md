# Methods

## Protocol, fixed before any number was taken

- **Splits.** FIT 60 / SELECT 20 / TEST 20 per dataset, or TEST 40 % when a set
  has 500 rows or fewer. Rows are grouped so that every question about the same
  state lands in the same split; a state whose questions are spread across FIT
  and TEST leaks.
- **Labels.** `human`, `derived` or `simulated`, recorded per row, and never
  generated by a language model. Each set's README says which, because a number
  measured against derived labels is a different claim from one measured against
  human labels.
- **Calibration method.** Store the raw logits once, then fit one temperature
  per question type on FIT and select on SELECT. No fine-tuning. A content-free
  prior is only applied if it moves ECE by at least 0.02 on SELECT, and option
  shuffling comes last.
- **Pass and fail, set in advance.** ECE_test below 0.05 for `noul` and
  `choice`, below 0.08 for `score`; Brier must decrease; accuracy must not move;
  dropping the least-confident 20 % must raise accuracy by at least 5 points.
  Failing ECE while passing the selective test is publishable as
  "ranking-useful, not calibrated", and is reported that way rather than
  rounded into a pass.

## How to read the numbers

**Accuracy is printed next to the majority-class rate.** 0.75 on a task whose
majority class is 0.795 is worse than a constant, and only the pair says so.

**Every table states its configuration.** Backend, `PAD`, `ctx/seq`,
`n_seq_max`, catalogue slots, batch size, and T. On the llama.cpp fork the
logits depend on the memory shape, not only on the tokens: raising `n_seq_max`
from 12 to 13, forced because four catalogue slots occupy four sequences, moved
one scenario score by up to 0.024 with nothing else changed. Two tables are
comparable only if both state these.

**`PAD` belongs to the backend, and is part of every number.** Padding the
shared prefix to a cache-block multiple buys a cross-call prefix hit on vLLM,
where it took a repeat call from 809 ms to 42 ms. The fork has no such cache, so
there the same padding is pure cost: it stretched a 121-token prompt to 1056 and
made a full collect 4.9x slower for accuracy unchanged within ±1.2 points. A
padded and an unpadded number are two configurations, never two runs of one.

**Score accuracy has two definitions and every score number names one.** Within
one level is what the fit reports; exact match is stricter. On the same
nvd2023_v2 rows they read 0.687 / 0.724 against 0.306 / 0.373. A table that
mixes them, or quotes one against a published row built from the other, is wrong
while looking right.

**n below 50 is a signal, not a result.** A probe of 6 rows once inflated a mass
gap by 3x, from −0.078 down to −0.025 at n=401.

**A number that fits both the hypothesis and its null proves nothing.** If "cache
hit" and "cache miss" both predict about 130 ms, the test has to be redesigned
until they diverge, not run again.

**Batched collects report flips three ways.** Right to wrong, wrong to right,
wrong to wrong, against the label, never as a single churn figure: 50 flips that
are 15 / 12 / 23 with accuracy moving 0.6141 to 0.6134 are noise, and one number
cannot show that.

**Speed claims are checked against the physical floor.** Prefill runs at roughly
0.25 ms per token at 2K and worse beyond it, a 528-token block is about 120 ms,
and per-request overhead is about 60 ms. A number that beats the floor is a
broken measurement, not a fast engine. CPU planning and GPU time are always
timed separately: a 2.1 s "GPU anomaly" turned out to be CPU tokenisation.

## Engine invariants

Eight rules the engine holds itself to. Each has an assert or a test, and each
was added after something went wrong.

1. **A scored token must appear verbatim in the catalogue**, with the same
   quoting. The model echoes the vocabulary it was shown, and labels beat
   instructions. Enforced by an assert in the prompt builder; the fix for a
   violation is to extend the catalogue, never to relax the check.
2. **The cache block size is read at runtime, never hardcoded.** The shared
   prefix is padded to a multiple of it and the last partial block is always
   recomputed. This one is vLLM's invariant, not the engine's, which is why the
   default follows the backend.
3. **Prompt order is `[catalogue][pad][state][pad][requests]`**, so the
   catalogue's blocks hash identically across states and the cross-call prefix
   hit is possible at all. A varying state at the top invalidates every block
   after it.
4. **One `generate()` call per state.** In-batch prefix sharing is where the
   7-10x comes from; a second "warm" call is pure loss.
5. **Window encoding never re-encodes the full prompt per option.** The engine
   picks a suffix that re-encodes standalone, widening by 8 tokens when a BPE run
   straddles the boundary. A full re-encode per option cost 2.1 s of CPU on the
   255-option preset. The oracle test compares window-encoded paths against
   full-encode paths for every option in every shipped preset, and prints how
   many options and cases it covered.
6. **Probabilities are renormalised over the candidate set and uncalibrated at
   T = 1** unless a table says otherwise. Said in every output and every report.
7. **`low_evidence` fires when `in_set_mass` drops below 0.5.** With correct
   prompts the mass is 0.99 or better, so a low flag is a prompt or formatting
   bug, not a hard question. Fix the prompt; do not tune the threshold.
8. **Backend metadata travels in `SamplingParams.extra_args`**, a field the
   stock sampler ignores. That is how the engine hands the fork the catalogue
   length without a second code path or a patched vLLM.

## Verification

`python -m tests.test_cpu` is the gate: no GPU, no weights, and it must pass in
a fresh clone rather than on a machine that happens to have a model lying
around. It currently runs 64 checks.

Two properties of that gate matter more than the count. A check whose dataset
this repository does not ship reports **skip** with the reason and is counted
separately, because a deliberate absence recorded as a pass misstates how much
was actually checked. And because every assertion in it is about where token
boundaries fall, the tokenizer is pinned by fingerprint: vocabulary size plus
the ids of the probes the assertions depend on. A different tokenizer fails the
first check by name instead of quietly changing what the other 63 mean.

Two rules that came from being burned:

- **A check may not filter or summarise the output it judges, and must state how
  much evidence it consumed.** A byte-identity check once diffed two logs from
  runs that had both died at startup, found no difference between two empty
  files, and printed "byte-identical". Print the producer's output verbatim on
  failure, print the row counts being compared, and make `n < 1` a third verdict
  rather than a pass.
- **A committed artifact must be what its generator writes.** A manifest once
  carried a block the builder never emitted: accurate, but added by hand, so
  rerunning the builder silently produced a different file. If a committed file
  says something its generator does not, fix the generator.
